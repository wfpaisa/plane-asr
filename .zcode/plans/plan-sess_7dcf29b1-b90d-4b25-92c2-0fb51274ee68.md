# Plan: CPU/GPU selector, Spanish i18n, Models UI overhaul, optional flags

Four coupled changes to the Plane ASR extension. Decisions on the two open questions use the recommended defaults (documented inline). All edits follow repo conventions (NodeNext `.js` imports, 4-space indent, single quotes, schema+`SETTINGS_KEYS` kept in sync, `pnpm run build` + `pnpm run lint` as the gate).

## 1. Binary mode: CPU / GPU (replaces Automatic / Manual)

**Open Q resolved (default):** CPU = bundled/PATH (auto); GPU = manual path to a Vulkan/CUDA build. GPU selection also forces `accelerator = vulkan` + auto-detect ON so the compute actually lands on the GPU. This is option 3 of the CPU/GPU question.

### Settings & schema (`cli-mode` semantics)

`cli-mode` keeps the same key/choices but its meaning is reinterpreted. To avoid ambiguity I rename the internal choice **`manual` → `gpu`** (so stored values are `cpu` / `gpu`), and add a tiny migration: on load, an old `'manual'` value maps to `'gpu'`.

- `schemas/org.gnome.shell.extensions.planeasr.gschema.xml`: change `<choice value="manual"/>` → `<choice value="gpu"/>`, update summary/description. Add a migration note.
- `src/config/settings.ts`: `CliMode = 'cpu' | 'gpu'`; add helper `normalizeCliMode(v)` that maps `'manual'/'auto'` → `'cpu'`, `'manual'` → `'gpu'`.
- `cli-resolver.ts`: rename `resolveAutoCli` → keep it (used for CPU mode). The function is unchanged; only callers reinterpret. No rename needed to limit churn.

### Transcriber (`transcriber.ts:_resolveCliPath`)

- `mode === 'cpu'` → bundled binary then PATH (current `resolveAutoCli` path).
- `mode === 'gpu'` → `cli-path` verbatim (current `manual` path).

### Backends (`asr-backends.ts`)

No change to argv building (flags already driven by `accelerator`). The accelerator is now set by the UI sync (see below), not by the backend.

### Pref UI (`prefs/index.ts`) — `syncCliMode` rewrite

- `CLI_MODE_IDS = ['cpu', 'gpu']` with labels `_('CPU')` / `_('GPU')`.
- Combo subtitle explains: CPU uses the bundled `transcribe-cli`; GPU lets you point to a custom Vulkan/CUDA build.
- **GPU explanatory note:** a caption `Adw.PreferencesRow` shown only when GPU is selected: _"GPU mode uses a manually configured binary (e.g. a transcribe.cpp build with Vulkan/CUDA). Point it to the compiled `transcribe-cli`, and the accelerator is forced to Vulkan so inference runs on your GPU."_
- `cliPathRow` shown only when GPU (like old manual).
- `cliStatusRow` (resolved binary) shown only when CPU (like old auto).
- **Side effect of selecting GPU:** on `notify::selected`, if id==='gpu', also set `ACCELERATOR='vulkan'` and `AUTO_DETECT_GPU=true` (drives `accelRow`/`autoDetectRow` via their existing `settings.connect`). Selecting CPU leaves accelerator untouched.

### Validation (`validateSetup` + `asr-service._validateCliBinary`)

Swap the `mode === 'manual'` checks to `mode === 'gpu'`; everything else identical.

## 2. Spanish (es) localization

**Open Q resolved (default):** standard gettext `.po/.mo` shipped inside `locale/`. This is the GNOME Shell-blessed path and matches the `initTranslations()` mechanism confirmed in the type defs.

### Prerequisites

The host must have `gettext` (`xgettext`, `msginit`, `msgfmt`) installed. The Makefile will check for `msgfmt` and error clearly if missing (same pattern as the existing `zip` check).

### metadata.json

Add `"gettext-domain": "planeasr"` so the domain is explicit and decoupled from the UUID (cleaner `.mo` filename: `planeasr.mo`).

### Init translations

Confirmed from type defs: `ExtensionBase.initTranslations()` is **not** called automatically; the current code's `import {gettext as _}` works only because GJS falls back, and bundled translations won't load. Fix:

- `src/extension/index.ts`: add `constructor(metadata) { super(metadata); this.initTranslations(); }`.
- `src/prefs/index.ts`: same constructor + `initTranslations()`.
  This binds `<extdir>/locale` for domain `planeasr` and makes every `_('...')` resolve through it. (Per the AGENTS.md lifecycle gotcha, avoid class-field initializers with side effects; the constructor body is safe.)

### Translation sources

- New dir `po/` with:
    - `LINGUAS` → lists `es`.
    - `Makevars` (standard gettext template: DOMAIN, XGETTEXT options, `--keyword=_ --keyword=N_ --keyword=C_:1c,2 --keyword=NC_:1c,2`, `copyright_holder`, `PACKAGE_GNU_MESSAGE`).
    - `POTFILES.in` → every `src/**/*.ts`, `extension.ts`, `prefs.ts` that contains translatable strings.
- `xgettext -f po/POTFILES.in -o po/planeasr.pot` generates the template. (Configured via Makevars; first run uses `make po/planeasr.pot`.)
- `po/es.po`: Spanish translation of **all** `_('...')` strings in the extension + prefs (model row labels, combos, tooltips, notifications, the new GPU note, etc.). I'll generate the pot, `msginit -l es`, then hand-translate every msgid to es (the strings are short UI labels — the existing `LANGUAGE_DEFAULT_NAMES`/labels like "Spoken language" → "Idioma hablado", "Download" → "Descargar", "Use" → "Usar", etc.).
- Build outputs `.mo` to `po/es.mo` (or directly to `dist/locale/...`).

### Build / pack

- `Makefile`: new target that compiles each `.po` into `dist/locale/<lang>/LC_MESSAGES/planeasr.mo` via `msgfmt`. Concretely add a `locale` step to the zip prerequisites:
    ```
    locale:
        @for po in po/*.po; do \
            lang=$$(basename $$po .po); \
            mkdir -p dist/locale/$$lang/LC_MESSAGES; \
            msgfmt -o dist/locale/$$lang/LC_MESSAGES/planeasr.mo $$po; \
        done
    ```
    and add `locale` to the `$(NAME)@$(DOMAIN).zip` prerequisites so it ships in the package.
- `package.json`: add a `"i18n"` script (`xgettext` regen + `msgfmt`) for convenience; `setup` continues to go through `make`.

### Important detail

The `locale/` directory **must exist** in the installed extension or the Shell silently falls back to system locale (per the `initTranslations` implementation). Shipping at least `locale/es/LC_MESSAGES/planeasr.mo` satisfies that.

## 3. Models page UI overhaul

Goal: make the catalog-model vs. custom-path distinction obvious, drop the need for `-m` when using a catalog model, and add a delete button.

### General page "Model" group (cleaner separation)

- The current `modelParamsRow` ("Advanced model params") is the **custom model path** entry. Rename title → `_('Custom model path')`, placeholder shows a full path with **no `-m`**: e.g. `/home/user/models/parukeet-0.6b-Q8_0.gguf`. Update its help/tooltip to clarify this is only used when no catalog model is selected.
- `refreshActiveModel` already shows catalog-model summary vs. the "no catalog model" fallback — keep it, tweak wording so it reads: catalog model → "Active catalog model: <name> …"; none → "Using custom model path (see field below)".
- The `openModelsBtn` ("Models →") stays to jump to the Models tab.

### Transcriber (`_resolveModelParams`)

- Catalog model active + on disk → inject `-m <path>` (already does; keep — the `-m` is added programmatically, the user never types it).
- **Custom path (no catalog model):** today it passes `model-params` raw, expecting the user to type `-m`. Change: when no catalog model is active and the `MODEL_PARAMS` value is a bare path (no `-m`/`--model` token and looks like a file path), inject `-m` automatically. Reuse the existing `extractModelPath` logic inverted: if `parseArgs(params)` has no `-m` and the string is non-empty, wrap as `-m <path> <rest>`. This makes `-m` optional in the UI as requested.

### Models page (`models-page.ts`)

Three concrete changes per catalog row:

1. **Path clarity / no `-m`:** the row's "Use" action already sets `ACTIVE_MODEL_ID` and the transcriber injects `-m`. Add a visible subtitle line showing the on-disk path of the selected quant once downloaded (e.g. `~/.cache/planeasr/models/<file>`), so the user sees the concrete path that will be used. Update `buildSubtitle`/`updatePresence` to include the resolved path when `isPresent`.
2. **Delete button:** add a `Gtk.Button` (destructive style, `user-trash-symbolic`/`edit-delete-symbolic`) to the controls line, shown only when the model is downloaded (`isPresent`). On click: confirm via a lightweight `Adw.MessageDialog` ("Delete model file <name>?"), then call `getModelDownloader().delete(entry, file, modelDir)`. After delete, refresh presence via the existing `model-deleted` signal (already wired in `model-store.ts` → emit on delete, which I'll connect in `applyFilter`/store listeners to flip the row back to "Download").
    - The downloader's `delete(entry, file, modelDir)` deletes the **selected quant's** file. Wire it to `selectedFile()`.
3. **Distinguish "downloaded (in catalog list)" visually:** when `isPresent`, add a "Downloaded" badge (`badgeLabel(_('Downloaded'), 'success')`) to the badge box, alongside existing Recommended/Streaming/parameters/backend badges. Keep "Use"/"Download" button semantics.

### Store wiring

`buildModelsPage` already connects `download-progress/complete/failed/cancelled`. Add a `model-deleted` handler that sets the row's presence back to false and toasts `_('Model deleted: %s')`.

## 4. Optional CLI flags field (General page)

Add a free-text setting for extra flags appended to every invocation, left blank by default.

- Schema: new key `extra-cli-flags` (type `s`, default `''`), summary "Extra CLI flags".
- `settings.ts`: `EXTRA_CLI_FLAGS: 'extra-cli-flags'`.
- `prefs/index.ts`: new `entryRow(_('Optional extra flags'), _('e.g. --verbose --beam-size 4 (left blank = none)'))`, placed in the **Transcription** group near the backend/CLI rows. Bind to the setting.
- `transcriber.ts:_buildArgvOptions`: read `EXTRA_CLI_FLAGS`; pass through `BuildArgvOptions` as a new `extraFlags: string` field.
- `asr-backends.ts`: extend `BuildArgvOptions` with `extraFlags?: string`, and in each backend's `buildArgv`, append `...parseArgs(opts.extraFlags ?? '')` right before the audio path (after model params + feature args + realtime). For the `custom` backend, append after template rendering. This keeps them "user wants these too" flags.
